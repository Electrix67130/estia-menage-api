# Contexte produit — Estia Clean Connect

> Carte fonctionnelle de TOUT le produit (les 4 apps). Lue automatiquement à chaque session.
> **À mettre à jour à chaque modification fonctionnelle** (nouvelle feature, changement de flux, déploiement).
> Rester concis : c'est une vue d'ensemble, pas la doc détaillée (voir `docs/API.md`, `docs/MCD.md`).

## C'est quoi

Gestion de prestations de ménage pour conciergerie de locations courte durée (Airbnb…).
Une conciergerie (org) gère des **logements** et des **prestataires** ; chaque intervention datée = une **prestation** (ménage, check-in ou check-out).

> ⚠️ **Publier une OTA : `npm run ota`** (et non `eas update` à la main). Ce script lance d'abord `scripts/check-ota-safe.mjs`, qui **bloque la publication si une dépendance native a été ajoutée depuis le dernier build natif** — une OTA ne livre que du JS, et un module natif absent du binaire fait planter l'écran qui l'importe, sans aucun signal au build ni à la publication. Vécu avec `expo-haptics` (ajouté le 21/07, binaire du 02/07) : deux mois de crashs sur l'onglet Calendrier. Deux issues quand il bloque : lancer un build natif, ou charger le module paresseusement (modèle : `src/lib/haptics.ts`). Contournement conscient : `OTA_GUARD_SKIP=1`.
>
> ⚠️ **OTA mobile — toujours `--environment production`.** Sans ce flag, `eas update` inline le `.env` **local** (`EXPO_PUBLIC_API_URL`/`_API_KEY` = localhost) dans le bundle prod → l'app pointe vers l'API locale et le login casse. Les vraies valeurs sont dans les variables d'env EAS (environment `production`).

**Pays de distribution (décision 08/10/2026)** : **France, Belgique, Suisse, Luxembourg** uniquement (App Store : appliqué le 08/10/2026 ; Play Store : à faire à sa publication). Hors de ces pays rien n'est prêt : facturation aux règles françaises, pages légales en français, recherche d'adresse limitée à FR/CH/LU/BE. Ouvrir un pays = décision délibérée qui traite ces trois points.

**Parité** : toute feature doit être déclinée dashboard **et** mobile quand elle concerne les deux (sauf facturation/gains = dashboard-only).

## Rôles

- **admin** : accès total à son org (logements, prestations, prestataires, facturation, gains).
- **prestataire** : voit/pointe les prestations des logements auxquels il est affecté ; ne crée pas de logement.
- Accès fin par logement via `logement_member` (permissions : voir clients, etc.).
- **Confidentialité client** : l'annuaire (`GET /clients`) est **admin only** ; une fiche client n'est lisible par un non-admin que s'il a `can_view_clients` sur un logement de ce client (`false` par défaut pour un prestataire). L'onglet **« Clients » de l'écran Équipe est masqué aux non-admins** (dashboard + mobile), et la fiche logement d'un non-admin ne charge plus l'annuaire complet — seulement le client du logement, s'il y a droit.

## Entités principales

`logement` (bien paramétrable : checklist, consommables, calendriers iCal, toggles check-in/out, codes d'accès) · `menage` (= prestation datée ; `prestation_type` ∈ menage/check_in/check_out) · `menage_check_section`/`menage_check_item` (checklist auto-générée) · `logement_member` · `photo` · `comment` · `client` · `invoice`/`invoice_line` · `logement_consommable` · `logement_code` · `logement_equipement` · `menage_prestataire` (multi-affectation) · `logement_external_calendar` · reschedule requests · device tokens (push).

## Fonctionnalités clés

- **Prestations** ménage / check-in / check-out, avec **tag de type coloré** (Ménage=bleu, Check-in=vert, Check-out=rouge) partout : listes, détail, cards calendrier, dashboard.
- **Sync iCal** (Airbnb, Booking, channel managers type PassPass/Cozysmart…) : chaque réservation génère un ménage + (si toggles `enable_check_in`/`enable_check_out` du logement) une prestation check-in/out. Dédup par `external_event_uid` + `prestation_type`. Le parser tolère un **`UID` absent** (certains ré-exports n'en émettent pas — sans repli leurs réservations étaient **silencieusement ignorées**, donc aucun ménage créé) : identifiant dérivé du `SUMMARY` s'il est id-like, sinon hash `cal_id|dates|summary`. Le message de fin de sync affiche les **événements lus** (`fetched_events`) en plus des créés/mis à jour/annulés (dashboard + mobile) et alerte quand le flux est vide ou qu'aucune prestation n'est impactée. **Retirer une presta auto** : la supprimer la marque `sync_ignored` + `annulé` (pas de hard delete, sinon la sync la recrée) → elle ne réapparaît plus au pull ; **« Remettre »** depuis le détail (dashboard : Historique → prestation ; mobile : écran **Historique** accessible via l'onglet Prestations, bouton « Remettre » sur les retirées — réservé à l'admin). **L'historique presta ne liste que les prestations qu'il a réellement faites** (affecté : référent OU co-presta), pas toutes celles des logements dont il est membre — via `GET /menages?assigned=me`. L'admin garde la vue complète. GC hard delete auto une fois **passée + disparue du feed**. Presta **manuelle** = hard delete définitif.
- **Checklist** par logement (modèles réutilisables). Chaque section a une **icône emoji** optionnelle (palette + « aucune ») choisie dans l'éditeur de template (mobile + dashboard), reportée sur la checklist générée.
- **Création manuelle** d'une prestation (mobile, FAB admin) : sélecteur de type ; formulaire adapté (check-in/out = heure unique, pas de durée/linge).
- **Qui est dispo ? (vue admin)** : sur chaque prestation **sans prestataire**, un **badge à trois états** calculé depuis les votes Présent/Absent (`present_count` / `absent_count` / `member_prestataire_count` renvoyés par `GET /menages`) : **vert « n dispos »** (+ prénoms) quand au moins un presta a dit Présent → bouton « Affecter » ; **rouge « Personne de dispo »** quand tous ceux qui ont répondu sont Absents ; **gris « Aucune réponse »** quand personne n'a voté → bouton **« Relancer »** (`POST /menages/:id/relance`, admin : push `relance` aux membres presta du logement qui n'ont pas répondu, réutilise la mécanique du rappel de la veille). Dans **À traiter**, la section « Sans prestataire » est **scindée** : « Quelqu'un est dispo » en tête (action immédiate), puis « Personne de dispo » (relancer / chercher). Le **sélecteur d'affectation** (dashboard + mobile) groupe les prestas **Disponibles / Sans réponse / Indisponibles** (grisés mais sélectionnables) grâce à `response_status` sur `GET /menages/:id/eligible-prestataires`, avec « Relancer les n » sur le groupe sans réponse. Filtre API `availability=available|unavailable|no_response`. Avant : les votes n'étaient visibles que dans le détail d'une prestation.
- **Filtre « Non assigné »** dans le filtre prestataire (mobile + dashboard) pour lister les prestations sans prestataire. Détail : tous les prestataires affectés (multi-presta) sont affichés, avec un badge **« Référent »** sur le principal. L'admin peut **désigner le référent** parmi les prestas affectés (bouton « Définir référent » sur les autres — dashboard + mobile) via `PUT /menages/:id/prestataires/:user_id/primary` (met à jour `is_primary` / `menage.prestataire_user_id` sans changer la liste).
- **Badges « non lus »** (commentaires / commentaires d'étape / photos ajoutés par un autre après ta dernière ouverture) : compteur par prestation (🔔 sur chaque ligne, dashboard + mobile) + badge de nav. Le badge est **ventilé par type** (`by_type` : le badge « Ménages » du dashboard ne compte que les ménages, Check-ins/Check-outs ont le leur ; mobile = onglet unifié). Ne compte **pas les prestations clôturées** (valide/annule → Archives), donc chaque badge = une ligne visible dans la liste active. **Périmètre presta** : un prestataire n'est notifié que pour les prestations où il est **affecté** (référent OU co-presta) — être simple membre `prestataire` d'un logement ne suffit pas (sinon une photo/un commentaire posé par un autre presta sur SA prestation créait un badge parasite). Seuls les membres de rôle **`manager`** (superviseurs) gardent les badges sur tout le logement ; l'admin voit tout. **Anti « badge fantôme » (dashboard)** : si un ménage avec du nouveau est masqué par les filtres actifs (statut/logement/presta/période/recherche), un bandeau le remonte en tête de liste avec lien direct + « Réinitialiser les filtres ». Les filtres de la liste étant **mémorisés** (persistés), une **barre « Filtres actifs : … · Réinitialiser »** s'affiche dès qu'un filtre est appliqué (**dashboard + mobile**). Le filtre **Créateur** range les prestations iCal sous « Airbnb », pas sous un admin.
- **Mentions dans les discussions** (`@`) : en tapant `@` dans un commentaire (fil général ou d'étape, **dashboard + mobile**), une liste propose les personnes qui **suivent la prestation** (`GET /comments/mentionable` = destinataires de ses notifications : créateur, admins, prestas affectés, managers/propriétaires — pas un presta simple membre du logement). Le texte garde « @Prénom Nom » en clair, les ids partent dans `mentioned_user_ids` (table `comment_mention`). La mention est **surlignée** dans le fil. La personne mentionnée reçoit **« X t'a mentionné »** avec le début du message, **à la place** de « Nouveau commentaire », et **même si elle a coupé les commentaires** : les mentions ont leur propre réglage (catégorie « Mentions »). À l'édition, seules les personnes ajoutées sont notifiées.
- **Photos + commentaires** par prestation. **Ajout multiple (mobile)** : le bouton « Galerie » ouvre le picker en **sélection multiple** (jusqu'à 30 photos), envoyées en une fois — traitement séquentiel (optimisation → upload → création), bandeau de progression « Envoi des photos 3/12… », boutons désactivés pendant l'envoi, une photo en échec n'annule pas les autres (récap à la fin) et **un seul refetch de la galerie** en fin d'envoi. La caméra reste photo par photo. Même traitement côté **dashboard** pour les photos de pièces d'un logement (l'`input` était déjà `multiple` ; c'est le refetch par photo qui a été supprimé, avec un libellé de progression « Envoi 3/10… »). **Pointage** arrivée/départ ; **validation** du rapport par l'admin — la modale de validation affiche un **récap du rapport** (note voyageurs + dégradations + photos du ménage) **dashboard ET mobile** (parité). La **déclaration voyageurs** (note 1-5 + dégradation) est saisie au pointage d'arrivée **et** ré-éditable après coup (`PUT /menages/:id/declaration`, presta assigné ou admin) — mobile + dashboard.
- **Calendrier** (dashboard + mobile, presta ET admin) : **vue mois**. Par défaut **vue classique** (pastilles + liste) ; une **case à cocher « Vue séjours »** bascule sur les **barres multi-jours** : chaque **séjour** = une barre colorée allant du check-in au check-out (regroupe ménage + check-in + check-out d'une réservation via `external_event_uid` ; arrivée = `date_prevue − stay_nights`), colorée par logement, en **couloirs** par semaine. **Demi-journées aux extrémités** : un check-out (matin) et un check-in (après-midi) le même jour tiennent **côte à côte** (turnover, pas de superposition) ; un **ménage** prend toute la journée **seulement s'il est seul ce jour-là** ; dès qu'il partage sa date avec une autre prestation, il se scinde et se cale sur la **moitié libre** (matin si l'après-midi est pris par un check-in/arrivée, après-midi si le matin est pris par un check-out/départ) — et **deux ménages le même jour** se répartissent matin/après-midi, sans jamais s'empiler sur un couloir séparé. Le split reste **basé sur le type** (iCal ET manuel) : check-in/arrivée = après-midi, check-out/départ = matin. **Dashboard** : infos check-in/out (icône + heure) sur les jours d'arrivée/départ + **clic ciblé** (jour d'arrivée → check-in, départ → check-out, milieu → ménage). **Mobile** : un **segmented control iOS à 3 vues** (remplace l'ancien switch) — **Séjours** (grille mois en barres multi-jours, fines et **couleurs adoucies/transparentes façon Apple**), **Prestations** (grille mois en points ; anciennement « Pastilles »), **Planning** (liste agenda de tout le mois). La **grille du mois remplit la majeure partie de l'écran** (cases hautes, semaines étirées en `flex` façon Calendrier Apple) ; la liste agenda du jour occupe le reste dessous. La **grille du mois occupe tout l'écran** (chrome resserré : month-nav/segmented/filtres compacts, la barre de filtres horizontale est bornée en hauteur pour ne pas laisser de vide au-dessus/en-dessous) — plus de zone détail permanente en bas. En Séjours, **tap sur une barre de séjour → détail de la prestation directement** (jour d'arrivée → check-in, jour de départ → check-out, milieu → ménage, même résolution que le clic ciblé du dashboard ; zone de tap élargie par `hitSlop`). En Séjours/Pastilles : tap une case (hors barre) → **nouvelle page dédiée** `/day/[date]` (route, **pas une modale**) façon **vue jour de Calendrier Apple** (nos couleurs) : header retour + mois, **bandeau semaine swipeable** (L→D, jour sélectionné en pastille couleur app ; tap un jour = change de jour sans quitter la page ; **swipe horizontal = changer de semaine**, FlatList paginée), **titre de colonne** « jeu. — 2 juil. », puis **timeline horaire façon Calendrier Apple** (gouttière d'heures à gauche, chaque prestation = un bloc positionné par `horaire_prevu` et dimensionné par `duree_estimee_min`, **coloré par logement** — `logement_color`, fallback couleur de type — avec fond adouci/translucide ; le tag de type reste, lui, coloré par type ; les prestations qui se chevauchent se placent côte à côte en colonnes ; les prestations sans heure sont listées au-dessus). La page applique les mêmes filtres persistés que le calendrier. La timeline et les lignes agenda sont un composant partagé (`src/components/DayTimeline.tsx`). En Planning : **agenda plein écran** (SectionList qui prend toute la place) — tous les jours du mois ayant des prestations, groupés par jour avec **en-tête de jour collant**, chronologiques, en lignes agenda (heure à gauche, **liseré coloré par logement**, nom du logement + tag de type, prestataire/statut, badge « Non pointé »), **triées par heure** (un turnover se lit check-out → ménage → check-in). Numéro du jour façon Apple : **aujourd'hui en pastille bleue** (couleur de l'app), jour sélectionné en **pastille pleine**. Toute la logique de visibilité/filtres/permissions est conservée.
- **Onglet Prestations (mobile) — une question par vue**, admin comme prestataire, via un sélecteur segmenté **Planning · À traiter · Historique** (`src/components/prestations/`). **Planning** = qu'est-ce qui se passe : liste **groupée par jour** (Aujourd'hui avec date et « x / n terminées », Demain, puis les dates), résumé du jour en chiffres (aujourd'hui / en cours / non assignées / non pointées) ; nouvelle carte `PlanningCard` (l'heure remplace la date, prestataire en premier regard ou bouton **« Affecter »**, badges seulement hors de l'ordinaire : non lus, report en attente, **« Non pointé » qui remplace le statut**, en cours, à valider). **À traiter** (compteur sur l'onglet) = qu'est-ce qui m'attend, avec l'action à portée de pouce : **À valider** (« Tout valider » en en-tête), **Non pointées**, **Sans prestataire**, **Demandes de report** (Accepter / Refuser inline) — remplace les chips de statut, le sélecteur de période, le bouton Historique et le bouton Demandes de report. **Historique** = `HistoriqueList` partagé (un mois à la fois, filtre « Non traitées » pour les oubliées > 30 j via `stale_before`). Recherche et filtres (type / logement / prestataire / source) derrière **deux icônes** ; feuille `FilterSheet` avec pastille de compteur et bouton « Voir N prestations ». Sélection multiple (appui long) + actions groupées Valider (terminées seulement) / Annuler / Supprimer conservées. **Côté prestataire** : même sélecteur ; Planning par jour avec les votes Présent/Absent et bandeaux de statut inchangés ; À traiter = **À répondre** (vote ouvert sans réponse) + **Non pointées** (affecté, jour passé). **Pas de clôture automatique** (décision produit). **Dashboard (parité livrée en 0.1.87)** : même sélecteur **Planning · À traiter** sur les listes ménages / check-ins / check-outs (lien « Historique » vers `/archives`), résumé du jour, sections Aujourd'hui / À venir, vue À traiter avec « Tout valider », non pointées, sans prestataire et **demandes de report Accepter / Refuser inline** (`RescheduleCard`), filtres logement / prestataire / source repliés derrière un bouton « Filtres » à pastille. Plus de chips de statut ni de filtre « Passées » : le passé non traité vit dans À traiter (≤ 30 j) puis dans l'Historique (« Non traitées »).
- **Demandes de report** (reschedule) presta → admin, puis décision admin → demandeur. Un report **accepté** qui déplace la prestation prévient aussi les **autres prestataires affectés** (co-prestas) : ils n'ont rien demandé et découvriraient le déplacement sur place.
- **Annulation / report d'une prestation → prestataires affectés** (hors auteur de l'action) : « Ménage annulé » (PATCH `status: annule`, suppression, ou annulation par la sync iCal) et « **Ménage reporté** », dont le corps annonce la **nouvelle date et heure** (« Nouvelle date : mercredi 8 juillet à 14:30 — Villa X ») au lieu d'un vague « la date ou l'horaire a changé ». Soumis aux préférences de notifications (catégorie `assignment`).
- **Suppression de compte depuis l'app** (`DELETE /auth/account`, mot de passe demandé) — exigence App Store 5.1.1(v) remontée lors de la review 2.1 du 06/10/2026 : Profil → Sécurité → « Supprimer mon compte » (mobile) et Réglages → « Supprimer mon compte » (dashboard). Le compte est **anonymisé** (identité effacée, accès coupés, prestations à venir désaffectées), l'historique de l'org (prestations passées, commentaires, photos) survit. Refusé au **dernier admin d'une org peuplée** (transmettre le rôle d'abord). La page `/privacy` mentionne aussi cette possibilité.
- **Répondre, réagir, signaler, bloquer** (repris de Buildr, 09/10/2026 — **dashboard + mobile**) :
  - **Répondre à un message** (`reply_to_id`) : la réponse cite l'original (auteur + 2 lignes) ; tap/clic sur la citation → scroll + surbrillance de l'original. Original supprimé → la réponse reste sans citation. Pas de citation d'une autre prestation.
  - **Réactions emoji** (liste fermée 👍 ❤️ 😂 😮 😢 🙏 🔥, `comment_reaction`) : interrupteur, compteur par emoji, surligné quand c'est la sienne (mobile : mise à jour optimiste).
  - **Accès** : mobile = **appui long** sur un message → feuille avec la rangée d'emojis, Répondre, puis Signaler / Bloquer (messages des autres) ou Modifier / Supprimer (les siens) ; dashboard = **barre d'outils au survol** (emoji, répondre, signaler, bloquer).
  - **Signalement** (App Store 1.2, table `report`, remplace l'ancien `feedback` `type: report` dont les données ont été reprises) : un **message**, une **photo** (mobile) ou un **membre** (mobile, fiche collaborateur), avec un **motif** (inapproprié, harcèlement, hors sujet, autre) + précision. On ne signale que ce qu'on peut voir. **Push « Contenu signalé » aux admins** de l'org, jamais à la personne visée ; personne visée admin → remonte aussi à la console super admin. Traitement : page dashboard **« Contenus signalés »** (badge du nombre en attente dans le menu) — supprimer le contenu, désactiver le compte, traiter ou rejeter avec une note ; console `/admin/reports` pour toutes les orgs. Un admin ne voit jamais un signalement qui le vise.
  - **Blocage** (`user_block`, exigé avec le signalement par l'App Store) : personnel et silencieux — les messages, leurs citations et les photos de la personne bloquée disparaissent **pour soi seul** ; elle n'est pas prévenue. Liste « Utilisateurs bloqués » + Débloquer : mobile Profil, dashboard Réglages.
- **Signalements — bugs & suggestions** (`feedback`, **bugs et suggestions uniquement** depuis le 09/10 — les contenus signalés ont leur propre module) : n'importe quel utilisateur envoie un message (bug rencontré ou fonctionnalité souhaitée) depuis **mobile** (Profil → « Aide et signalements » : formulaire + historique de ses envois avec les réponses) ou **dashboard** (page « Signalements », bouton d'envoi ouvert à tous). Le message part avec son **contexte technique** (plateforme, version d'app, écran, langue de rédaction) — sans lui un bug mobile est irreproductible. Les **admins de l'org** traitent depuis le dashboard : onglets par statut (`new`/`in_progress`/`resolved`/`declined`, les nouveaux d'abord), recherche, réponse écrite → **push à l'auteur** (`feedback_reply`) et passage automatique en « traité ». Repris de Buildr. **Deux niveaux de traitement** : les **admins de l'org** (page « Signalements ») pour leurs propres membres, et le **super admin** (`/admin/feedback`) pour toutes les organisations.
- **Réponses présent/absent** : dans la liste presta (mobile), le vote Présent/Absent (ou le pill « Présent » verrouillé quand il est retenu) n'apparaît **que sur une prestation « à venir »** ; tout autre statut **ou tout jour passé** affiche un **bandeau de statut** — en cours, terminé, **« Validée · fait par X »** (vert), **« Annulée »** (gris), **« Non pointée — pointe ton arrivée depuis la fiche »** (rouge, affecté) ou **« Passée · personne ne l'a prise »** (gris) — avec carte atténuée pour les clôturées, sinon une prestation finie ressemblait à une prestation future. L'admin n'est notifié que si la réponse du prestataire **change** — re-poster le même statut (re-clic, re-confirmation après affectation) ne redéclenche pas de push.
- **Réglages des notifications** (inspirés de Buildr, 09/10/2026), trois niveaux appliqués à **toute** push (`lib/notification-preferences.ts`) : (1) **interrupteur général** `push_enabled` — « Recevoir les notifications » coupe tout, mentions comprises ; (2) **catégories** (affectation, dispo, rappels, reports, présence, pointage, validation, commentaires, **mentions** — indépendante des commentaires —, consommables, invitations, **contenus signalés** pour les admins) ; (3) **par logement** : **Tout / L'important / Rien** — « L'important » = mentions, affectations, rappels (ce qui me concerne personnellement). Écrans : mobile Profil → Notifications (+ sélecteur sur la fiche logement) ; dashboard Réglages → Notifications (+ sélecteur sur la fiche logement). Les logements réglés sont listés avec « Tout recevoir ».
- **Notifications push** (Expo) + **emails brandés** ; **rappels programmés** (veille 18h, 2h avant). **Alerte admin « Lits à renseigner » (veille 9h)** : si un ménage du lendemain n'a **aucun couchage renseigné** (`n_lit_simple + n_lit_double + n_canape_lit + n_lit_appoint + n_lit_parapluie = 0`), les admins de l'org reçoivent une push (`type: beds_missing`, catégorie de préférence `reminders`) — uniquement pour `prestation_type = menage` (pas de linge sur check-in/out), une seule fois par prestation (anti-doublon `reminder_beds_sent_at`). **Destinataires d'une prestation** (`getMenageRecipientIds`, push + realtime) = créateur + admins de l'org + prestas **affectés** (référent + co-presta) + membres `manager`/`client_proprietaire`. Un membre de rôle `prestataire` **non affecté** n'est pas notifié (même règle que les badges non-lus).
- **Codes d'accès multiples** par logement (`logement_code`) : autant de codes que nécessaire, chacun avec un **libellé personnalisé** (« Boîte à clés », « Portail », « Alarme », « Wi-Fi »…) + notes. Remplace le champ unique `key_safe_code`, retiré des formulaires d'édition (dashboard + mobile) au profit d'une section **« Codes d'accès »** (code masqué, révélé au tap/clic). **Écriture admin** ; **lecture** pour l'admin, les membres du logement **et le presta affecté à une prestation même s'il n'est pas membre** (sans le code il ne peut pas entrer). Le **détail prestation liste tous les codes** (dashboard + mobile) au lieu de la seule boîte à clés. `logement.key_safe_code` survit en **miroir du premier code** (resynchronisé à chaque écriture) : la jointure `logement_key_safe_code` et les anciens clients continuent de marcher, et un `key_safe_code` envoyé à la création alimente la liste sous « Boîte à clés ».
- **Couchages** : 5 compteurs par logement (valeurs par défaut) et par prestation (valeurs effectives, éditables par l'admin) — lit simple, lit double, canapé-lit, lit d'appoint, **lit parapluie**. Affichés en « Lits à faire » sur le détail prestation (dashboard + mobile), avec suggestion depuis le nombre de voyageurs.
- **Équipements à préparer** par prestation (`menage_equipement`) : l'admin coche, dans l'inventaire du logement, ce que le prestataire doit sortir/installer pour cette intervention (chaise haute, baignoire bébé, lit parapluie…). Section **« À préparer »** sur le détail prestation (dashboard + mobile) avec compteur `préparés/total`. **Le prestataire est en lecture seule** : il consulte ce qu'il doit installer, il ne coche rien — seul l'admin configure la liste et suit l'état (`done_at`/`done_by`). Ré-enregistrer la liste **ne décoche pas** ce qui est déjà marqué préparé. `PUT /menages/:id/equipements` et `PATCH /menages/:id/equipements/:equipement_id` = **admin only**.
- **Options / packs** (`logement_option` + `menage_option`) : packs proposés au client sur un logement (**pack romantique**, **pack anniversaire**, panier gourmand…), configurés par l'admin dans la fiche logement (libellé libre + description « à installer », suggestions servies par l'API). Sur une prestation, l'admin coche **l'option retenue par le client** ; elle s'affiche en évidence sur le détail (dashboard + mobile) pour que le prestataire l'installe — **lecture seule côté presta**, comme les équipements à préparer. `PUT /menages/:id/options` = admin only.
- **Inventaire des équipements** par logement (`logement_equipement`) : ce dont le bien est équipé (appareil à raclette/fondue, plaque de cuisson, lave-vaisselle…). **Écriture admin, lecture par tous les membres** (le presta doit savoir ce qu'il trouvera sur place). Chaque ligne = libellé libre + **famille** (cuisine/électroménager/confort/extérieur/loisirs/bébé/sécurité/autre) + quantité + **pièce** optionnelle (`logement_room_id`) + notes. Deux modes d'ajout, **dashboard + mobile** : le **catalogue** (`GET /logement-equipements/catalog`, suggestions servies par l'API donc identiques sur les 2 apps → sélection multiple, ajout groupé idempotent via `POST /logement-equipements/bulk`) ou la saisie libre. Affiché groupé par famille sur la fiche logement.
- **Console super admin** (`/super-admin/*`, dashboard `/admin/*`) : vue transverse à toutes les organisations, réservée au porteur du produit via `user.is_super_admin` (posé **à la main en SQL**, aucune route ne l'accorde). Vue d'ensemble (orgs/users/ménages + sièges facturables), gestion des **organisations** (kill switch `is_active`, impersonation 30 min pour le support), des **comptes** (activer/désactiver, couper les sessions, mot de passe temporaire, suppression), **signalements toutes orgs**, **journal d'audit** (toute action de super admin est tracée) et **journal d'erreurs** (les 500 de l'API). Le kill switch éteint réellement : `getActiveMembership` ne rend plus rien pour une org désactivée. Les pages du dashboard existaient déjà mais appelaient des endpoints inexistants — l'API est désormais en face.
- **Site vitrine** (`estia-clean-connect.fr`) : présentation du produit (accueil, fonctionnalités, comment ça marche, tarifs **sur devis**, contact) en **8 langues**, plus les deux pages **exigées par l'App Store** — `/support` (aide, contact, suppression de compte) et `/privacy` (RGPD) — et `/legal` (mentions légales). **Export statique** (`output: "export"`, ~2 Mo) servi par Caddy : pas de Node sur le VPS, dont le disque est déjà occupé à 80 %. Le contenu ne parle **pas que de conciergerie** : conciergeries courte durée, sociétés de nettoyage, propriétaires multi-biens. Les pages légales restent **en français** (le responsable de traitement l'est), avec une mention dans la langue du lecteur. Toutes les URLs et l'identité légale viennent de `src/lib/site.ts`. ⚠️ **À compléter avant mise en ligne** : `LEGAL_IDENTITY` (SIRET, siège, directeur de publication). ⚠️ Tant que le site n'est pas en ligne, la fiche App Store pointe `supportUrl`/`privacyPolicyUrl` sur `api.estia-clean-connect.fr` — bascule par simple `eas metadata:push`, sans rebuild.
- **Recherche d'adresse multi-pays** (fiche logement, dashboard + mobile) : on choisit la ville puis l'adresse, sur la base officielle de chaque pays — **France** (geo.api.gouv.fr + BAN), **Suisse** (api3.geo.admin.ch), **Luxembourg** (geoportail.lu : autocomplétion + géocodeur exact pour les numéros), **Belgique** (**Photon**/OpenStreetMap — pas de base nationale unique, une par région ; instance publique qui **limite le débit**, 503 si on la sature). Les villes des quatre pays sont fusionnées (drapeau dans la liste, nom exact en tête, 3 places au plus pour les villes étrangères, qui doivent contenir le texte saisi). Photon complétant au numéro près, une adresse belge n'est retenue que si sa rue contient les mots tapés ; numéro absent d'OSM → la rue seule est proposée. Hors de France le **code postal vient de l'adresse choisie** (il dépend de la rue) ; au Luxembourg, il est stocké avec son préfixe (`L-1610`). Un quartier de Luxembourg-Ville (Kirchberg, Gare…) trouve les adresses de localité postale « Luxembourg » (rayon de 3 km). Code : `src/lib/address-search.ts`, dupliqué dans les deux apps. **Géocodage API** (`src/lib/geocode.ts`, carte + rattrapage en masse) : le pays se déduit du code postal (5 chiffres → BAN, `L-1234` → Luxembourg, 4 chiffres → Suisse, puis Luxembourg, puis Belgique), et le résultat étranger doit porter le même code postal — et la même ville pour la Suisse (1000 = Lausanne **et** Bruxelles) — sinon rien plutôt qu'un point faux.
- **Consommables** par logement + alertes sous seuil. L'**unité** (texte libre : « rouleaux », « flacon », « L »…) est **accordée à la quantité** à l'affichage (`formatQtyUnit`, `src/lib/unit-fr.ts` dans le dashboard et le mobile) : « 1 rouleau » / « 3 rouleaux », singulier pour 0 et 1, abréviations et libellés composés laissés tels quels — quelle que soit la forme saisie par l'admin.

Mobile : vignettes en scroll horizontal par pièce + visionneuse plein écran (`react-native-image-viewing`) ; dashboard : grille + lightbox. Bandeau « ⏳ en attente d'envoi » sur le détail ; couvre ménage (arrivée+déclaration, départ) et check-in/out. Livrable en OTA (100 % JS).

## Règles métier notables

- Tarifs d'un ménage modifiables par l'**admin** uniquement.
- Affecter un prestataire à un ménage = **admin** uniquement.
- **Visibilité d'un ménage assigné** : une fois affecté à un prestataire, un ménage **n'est plus visible par les autres prestataires** (mobile + dashboard) — même s'ils sont membres du logement. Un membre `prestataire` ne voit que : ses ménages (référent/co-presta) + les ménages **non-assignés** (à prendre). Les membres `manager`/`client_proprietaire` et l'admin gardent la vue complète. Appliqué côté API (`GET /menages` liste **et** `GET /menages/:id` détail → 404 si un membre presta tente d'ouvrir un ménage assigné à un autre). Même esprit que [[presta-scope-assigned-not-member]].
- Montants « gains/facturation » comptés sur ménages **terminés/validés**. CA = `client_price_ht` (+ blanchisserie client) ; coût = `provider_price` (+ blanchisserie presta). **Les gains comptent les ménages réalisés même si leur logement est archivé ensuite** (l'archivage ne doit pas effacer l'historique financier). La page dashboard « Archives » (clôturés validé/annulé) est désormais nommée **« Historique »**.
- URLs internes `/files` signées à la lecture. **Perf images (mobile)** : les vignettes de la fiche prestation (photos de référence du logement, grilles imbriquées) se chargent **à la demande au scroll** (`src/components/LazyImage.tsx` : `LazyLoadScope` autour de la ScrollView + `LazyImage` qui se mesure à l'écran, marge 300 px ; sans scope parent → chargement immédiat) au lieu de toutes partir à l'ouverture — 100 % JS, OTA. **Prévu 1.0.1 (build natif)** : `expo-image` avec cache disque et `cacheKey` = nom de fichier pour survivre à la rotation quotidienne du jeton signé et au hors ligne. **Perf images (API)** : le token d'URL a une expiration **arrondie à une fenêtre** (avatar/cover 24 h, photos d'intervention 1 h) → URL stable → le cache client (navigateur/`<Image>` RN) est réutilisé (avant : token glissant → re-téléchargement à chaque affichage). `/files` pose un `Cache-Control` (fichiers immuables). `POST /upload` génère et renvoie une **miniature** `thumbnail_url` (~400px) pour toute image ; stockée à côté de l'original (`photo.thumbnail_url`, `user.avatar_thumbnail_url`, `logement.cover_photo_thumbnail_url`) et affichée dans les listes/grilles, l'original ne servant qu'en plein écran.
